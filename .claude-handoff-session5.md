### Uneek live API integration
- Uneek has a real API (`api.uneekclothing.com`, HTTP Basic Auth = same email/password as their website login, no separate API key). Docs at `/docs/index.html`, spec at `/swagger/v1/swagger.json`.
- **Critical quirk discovered and handled**: Uneek's API **double-encodes** its response — the HTTP body is itself a JSON string containing the real JSON as escaped text (`"[{\"Company\":...}]"`), not a bare array. `functions/_lib/uneek.js`'s `fetchUneekRawText()` unwraps this with one `JSON.parse()`.
- `functions/api/uneek-sync.js` (full-catalog sync) **hits Cloudflare's Worker CPU limit** on this account's plan when parsing/processing the whole catalog in one request (Error 1102). Its UI button was **removed from admin.html** (hidden, code/endpoint left in place, dormant) rather than fixed, since the per-code alternative below covers the actual use case.
- `functions/api/uneek-product.js` (per-product-code lookup, used by `add-product-live.js` when publishing a Uneek item) is CPU-cheap — does targeted substring extraction on the unwrapped text instead of a full `JSON.parse` + loop over every row. This is what actually works reliably.
- Env secrets: `UNEEK_EMAIL`, `UNEEK_PASSWORD`, `UNEEK_CUSTOMER_NO` (= `CRY08`) — confirmed set and working.
- The old PenCarrie-only "Sync Colours/Sizes" green button and "Import colours/sizes" CSV box are **hidden in admin.html** (`class="hidden"`, code intact) — superseded by the PenCarrie catalog migration below, which writes real colour/size data directly onto every row it creates.

### PenCarrie full catalog migration (the big one this session)
Martin's actual PenCarrie trade price file (`products-GBP.zip` → `products.csv`, ~223MB/~90k rows) has genuine per-**exact**-colour+size pricing (Single/Pack/**Carton** List Price tiers — Carton is the correct cost tier, confirmed against a real invoice). The **old** catalog model was coarse: one row per size *tier* (e.g. "S - XXL") with most colours collapsed into a generic bucket row whose label **varied per product** (confirmed both `"Colours"` and `"All Colours"`/size=`"All"` in live use — no single fixed string to match on).

- `functions/api/pencarrie-import.js`: switches PenCarrie products to one row per **exact** colour+size (new id scheme `pencarrie-<code>-<colour>-<size>`), matching Uneek's model. Upserts by natural key (code, colour, size) rather than the old rows' unknown id scheme. `sell_price` carried forward from whichever old row's size-tier covers the new exact size, matching colour name first, falling back to "old row's colour isn't a real colourway for this code = it's a bucket row" (robust to any label wording, not hardcoded strings).
- **223MB file had to be split into 28 sub-10MB CSV chunks** (Claude-in-Chrome's `file_upload` tool caps around 10MB per call) and run through Chrome automation against Martin's real logged-in session, since I have no direct D1 write access and can't authenticate as him. Split script pattern: Python `csv` module (handles the file's embedded multi-line HTML description fields correctly — a naive line-count split would corrupt it).
- **Real bugs found and fixed during/after migration** (all fixed, backfilled, and now prevented going forward):
  1. `on_website` flag wasn't carried forward → every already-published PenCarrie product silently lost its "on website" status. Fixed via `{backfillOnWebsite: true}` action (1,864 rows repaired).
  2. `supplier_ref` (PenCarrie's own reference codes, e.g. "TFC100") and the ON CONFLICT clause's `active = excluded.active` (would have silently reactivated anything manually deactivated, on any *future* re-import) — fixed via `{repairMigrationFields: true}` action (18,065 rows repaired) + removed `active` from the upsert's UPDATE SET entirely.
  3. **Pattern for next time**: whenever adding a migration/upsert like this, audit *every* column on the old row being superseded, not just the ones the task explicitly mentioned — two of these three were found only by deliberately re-auditing after the first (`on_website`) was reported by Martin as broken.
- Old (pre-migration) rows are **soft-deleted to Trash**, never hard-deleted — fully recoverable.
- The `{finalize: true, codes: [...]}` action retires old rows for a set of codes once their replacement new-format rows are confirmed in — **do not call finalize until every chunk of a run has been imported for real**, or you'll retire old data before its replacement is fully written.
- Uses `functions/api/products.js`'s existing `id`-based exact-match GET filter — **wait, this was added THIS session for a different reason** (see Services/fees fix below), so if working from an older checkout, that filter needs to exist for related features to work.

### Production tracker pipeline changed + backfilled
New default sequence (`functions/api/production-steps.js`'s `DEFAULT_STEPS`): **Invoice paid → Artwork sent for digitization → Garments ordered → Artwork approved → Ready for collection/dispatch → Order collected**. Dropped "In production" entirely.
- Only changes the default for trackers seeded from now on. Existing in-progress orders were backfilled via a `{migrate_pipeline: true}` POST action — reuses existing step rows in place (preserves any attached photos, which are linked by `step_id`) wherever a direct old→new mapping exists, infers done-status correctly (e.g. old "In production" done implies "Garments ordered" + "Artwork approved" are also done), and skips (leaves untouched) any order with a custom/renamed step rather than guessing. Result: 7 orders migrated, 1 skipped (custom "Quality check" step).
- `sendStepNotification`'s regex-based email-template picker matches on `/artwork/` in the step title — **watch out**: "Artwork sent for digitization" also matches that regex, so it deliberately defaults to `notify: false` to avoid firing the wrong ("approved") email wording early.

### Quote/Invoice builder improvements
- Inline "+ New" customer panel (used from the Order builder, distinct from the full Customers tab form) was missing every address field — added Type, Address 1/2, Town/City, County, Postcode to match.
- "+ Insert standard notes" button next to the quote/invoice Notes field — appends (never overwrites) Martin's "what happens next" copy (auto-invoice on acceptance, bank transfer preferred, logo proof before decoration). This field is customer-facing (rendered into the email), not internal.
- **New internal-only "🔒 Your margin" box** at the bottom of the builder (both quotes and invoices, same screen) — garment cost vs sell price and profit %, computed client-side, never saved to the order or sent to the customer. Decoration revenue is deliberately excluded (its cost isn't tracked, so including it would show fake 100% margin on that portion).
  - Needs `cost_price`/`vat_rate` tracked on each `orderLines[]` entry — added wherever a line's product gets set (catalog pick, customer price-list pick, new-product-in-order, `clearOrderLineProduct` reset).
  - **A saved order's `items` JSON never stored cost_price/vat_rate** (only ever stored what the customer's charged) — so reopening/reordering a saved quote left the margin box showing £0.00 for every line. Fixed via `attachCostDataToOrderLines()`, called after `mapOrderItemsToBuilderLines()` in both `reorderOrder()` and `editOrderInBuilder()` — re-looks-up current cost/VAT by `supplier_code` (preferring exact colour match).
  - **Follow-up bug** (found by Martin testing invoice #14, a polo + a Design Setup Fee): a flat fee/service line has **no `supplier_code`**, only a `product_id` — so it was silently skipped by the lookup above and contributed £0 cost, understating true margin. **This affects every Services-tab item generically**, not just that one fee. Fixed: added `?id=` exact-match filter to `products.js`'s GET handler (nothing could look a product up by bare id before this), and a second lookup pass in `attachCostDataToOrderLines()` for lines with `product_id` but no `supplier_code`. **Martin was independently re-verifying this fix when this session ended** — check with him whether invoice #14's reorder now shows correct margin before assuming it's fully confirmed.

### Invoice/quote document bugs (Martin-reported, all fixed)
1. **Archived items had no Reorder button** — added it to `archivedOrderRow()`, plus fixed the actual reason it would have silently failed anyway: the Archived modal's `openOrderArchive()` never populated `ordersById`, which `reorderOrder()` reads from.
2. **Reorder profit margin** — covered above.
3. **Decoration cost not itemized on the customer-facing PDF/email** — a garment row's "Total" column silently included decoration cost while "Unit" showed garment-only price, so e.g. "2 × £18" not matching that row's own Total looked like a maths error (real example: invoice #27, £36 garment + £10 decoration shown only as one combined £46). Fixed in both `functions/_lib/document-pdf.js` and `functions/api/send-email.js`: garment row's Total is now garment-only (`qty × unit_price`), decoration gets its own priced row(s) per distinct method+placement+price (collapsed across colours so it doesn't repeat per breakdown row).
4. **Manually recorded payment invisible on PDF/email until first send** — the "Paid to date"/"Balance due" display was gated on `email_sent_count` (a leftover "only ask for deposit once" rule) rather than on whether anything had actually been paid, even though `orders.amount_paid` was already correct in the DB the moment the payment was recorded. Now driven by `amount_paid > 0` directly, in both files. Also fixed the Status line's binary Paid/Unpaid to show "Partially paid" for `paid_status = 'partial'`.
5. **PDF text truncation → real word-wrap**: long item titles/decoration labels/notes were hard-truncated with "…" at a fixed character count (screenshot from Martin: "+ Embroidery - Right chest (INCLUDED MAIN L…"). Replaced with a proper greedy word-wrap using a full **published Helvetica AFM character-width table** (not an estimate — real font metrics for a PDF core-14 font) in `document-pdf.js`. **Caught before push**: the order Notes section (same field the "Insert standard notes" button fills) was still calling the now-removed `truncate()` and would have thrown a fatal error on any order with notes — fixed in the same pass, always double-check for other callers when removing a shared helper.

All four documents (PDF, invoice email, quote email) generate **fresh from live DB data on every request, no caching anywhere in the path** — confirmed via research this session — so all of the above fixes apply immediately to every existing quote/invoice, not just new ones.

## Environment / workflow notes new this session

- **`git push` can hang silently** in this environment — use `GIT_TERMINAL_PROMPT=0 timeout 60 git push` to avoid an indefinite hang (root cause not fully diagnosed, but this workaround was 100% reliable all session).
- **Git Credential Manager had two stored identities** (`farja-king` real account + a stray `x-access-token` token credential) causing an account-picker popup on every push — cleared via `git credential-manager github logout x-access-token`, kept the real one. If the picker reappears, `git credential-manager github list` / `logout <account>` is the fix.
- **Claude-in-Chrome's `file_upload` tool caps combined upload size around 10MB per call**, and multiple `file_upload` calls in the *same* `browser_batch` also count toward that combined limit (learned the hard way — batch one upload+run at a time, not several uploads together). Files must live somewhere the tool is allowed to read (the project working directory works; the session's own scratchpad temp dir does **not**, despite being described as accessible).
- **Unpaginated large fetches can freeze the Chrome tab** — `/api/products?trash=1` with no effective limit (~6,000+ rows) hung a `javascript_exec` call past its timeout once; opening a fresh tab and re-querying worked fine. Prefer targeted queries (by code/id) over full-table dumps when sanity-checking live data.
- **A `grep`-tool display artifact**: `//` in a comment was rendered back as a literal `\` in one Grep result this session, purely a rendering glitch — always double-check a suspected syntax bug with `Read` before concluding the source file is actually broken (wasted a bit of time chasing a phantom bug before catching this).
- Real syntax bugs **did** also occur for real this session (unrelated to the above) — e.g. a stray literal `\` instead of `//` at the start of a comment line, which is a genuine fatal JS parse error that silently prevents every function defined after it in the same `<script>` block from existing. If a function mysteriously shows `typeof fn === 'undefined'` in the browser console right after a deploy, check for exactly this before assuming a deploy-lag/cache issue (though deploy-lag is also real and common — try a cache-busting reload first, it resolved most `undefined` cases this session).
- Chrome automation flow for live-testing DB-touching endpoints (used repeatedly this session): `tabs_context_mcp` → `navigate` to `https://portal.embroidery.click/admin` (relies on Martin's real logged-in session cookie in his actual Chrome) → `javascript_exec` calling `fetch()` against the portal's own `/api/*` endpoints directly, or calling admin.html's own JS functions in-page. This is how every DB migration/repair/verification this session was actually executed and confirmed, not just written.
