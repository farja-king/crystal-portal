# Handoff: Part payments, deposits & receipts for crystal-portal

## The ask (from Martin, verbatim intent)
A Karl Sports invoice just had a part-payment made against it. He wants:
1. **Part payments / deposits**: request either a fixed £ deposit or a % deposit on an invoice; record partial payments against it (not just binary Paid/Unpaid).
2. **Populate everywhere**: the Dashboard, the Quotes & Invoices list, reminders, PDFs, emails - wherever payment status shows today should reflect partial payment state too.
3. **Mark Paid → a popup, not a one-click toggle**: entering an amount, presumably a date/method/notes, rather than the current single-click "Mark Paid"/"Mark Unpaid" button.
4. **Receipts/statements**: ability to send the customer a receipt/statement for a part payment showing balance due.
5. General steer: "add in any usual booking or accounting tools... usually integrated into such other software products" - he's open to a broader lightweight AR (accounts receivable) treatment, not just the minimum to tick the box.

## Current payment status model (what exists today)
- `orders` table (functions/api/orders.js): `doc_type` ('quote'|'invoice'), `paid_status` (only ever 'paid'|'unpaid', simple string), `paid_at` (set/cleared whenever paid_status flips), `total`, `due_date`.
- Mark Paid: admin.html's `setOrderPaidStatus(id, status)` - a single PUT `{id, action:'set_paid_status', paid_status}`, no amount/date/method captured, binary toggle. Button lives in the main Quotes & Invoices list row actions.
- Reminders (`functions/api/payment-reminders.js`): daily/15-min Worker-cron sweep chases anything `paid_status != 'paid'` past its due date, using the *full* `total` in the email wording - has no concept of partial payment today.
- Dashboard revenue (`admin.html`, `renderDashboard()` ~line 8617): `paidInRange = dashOrdersInRange(dashboardOrders, from, to, 'paid_at').filter(o => o.paid_status === 'paid')`, then `revenue = paidInRange.reduce((s,o) => s + o.total, 0)` - counts the *full order total* of anything fully paid, keyed off the single `paid_at` timestamp. `dashboardOrders` is fetched via `/api/orders?all=1` (an `?all=1` mode was added specifically so archived orders still count - see git history).
- PDF (`functions/_lib/document-pdf.js` via `functions/api/order-pdf.js`) and the emailed invoice HTML (`functions/api/send-email.js`) both show a flat "Total: £X" with no paid/balance breakdown.
- Manual invoices exist too (`functions/api/manual-invoice.js`, added this session) - PDF-uploaded invoices for Karl Sports specifically, `orders.is_manual=1`, no items, PDF comes from R2 not generated. **Payments need to work on these too**, not just system-built invoices.
- Shared nice-HTML email template: `functions/_lib/email-template.js`'s `emailShell({heading, bodyHtml, ctaText, ctaUrl, ctaColor})` - reuse this for any new receipt/statement email, it's what every other automated email in this app already uses (payment reminders, step-completion updates, review requests).
- Resend env vars already configured: `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, `RESEND_REPLY_TO`. `email_log` table (created lazily by `send-email.js`) is the shared send-history log everything else piggybacks on for an order's Communication History panel - any receipt email should log there too via `INSERT INTO email_log (id, order_id, sent_to, subject)`.

## Design decisions already reasoned through (worth keeping)
- **Schema**: add a `payments` table (id, order_id, amount, method, type ['deposit'|'payment'|'final'], notes, received_at, receipt_sent_at) as the real ledger - one row per payment received. Also denormalize a running `orders.amount_paid` (updated on every insert/delete against `payments`) so every existing place that reads `orders.*` (Dashboard, list badges, reminders) doesn't need a join to know "how much has been paid so far." `orders.paid_status` gains a third value: `'partial'`.
- **Deposits**: modeled as *fields on the order* (`deposit_amount` and/or `deposit_pct`) set at invoice time - shows on the PDF/emailed invoice as "Deposit due: £X". Paying it is just a normal row in `payments` (type='deposit') once it actually comes in - a deposit is a *request*, not a payment in itself.
- **Mark Paid popup**: replace `setOrderPaidStatus` with a "Record a payment" modal - amount (prefilled with the outstanding balance), date, method (Bank Transfer/Cash/Card/Other dropdown), notes, and a "send receipt" checkbox. Submitting inserts a `payments` row, recomputes `amount_paid`/`paid_status`, optionally sends the receipt.
- **Undoing a payment**: needs a small payment-history list (in the order view popup) with a delete/void action per row, recomputing totals afterward - a straight "Mark Unpaid" toggle doesn't make sense anymore once there's a ledger.
- **Dashboard revenue accuracy tradeoff** (this was the open question when we got interrupted): simplest option is to keep keying revenue off `orders.amount_paid` + a single last-payment `paid_at` date (small change to existing `paidInRange` filter/sum) - cheap, but a customer paying in two installments across two different months would have *all* of it land in whichever month the second payment happened. The more correct option is to fetch the `payments` table directly (new `?all=1` mode on a `/api/payments` endpoint, mirroring the existing `orders?all=1`/`production-steps?all=1` pattern) and bucket revenue by each payment's own `received_at` - properly accurate per-period reporting, moderately more work (touches `renderDashboardChart`/`renderDashboardTopCustomers` too, not just the top-line tile). Leaning toward recommending the accurate approach given Martin explicitly asked for "usual accounting tools," but this needs his sign-off before building - was about to ask this as a clarifying question when the session got cut.
