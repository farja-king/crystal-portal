### Stock/inventory got a major expansion this session
- **Reorder threshold + minimum stock level** (two separate numbers per item): `reorder_threshold` = "alert me at/below this" (defaults to 3 for every item via `DEFAULT_REORDER_THRESHOLD` in `_lib/stock-alerts.js`, matching `admin.html`'s client-side constant — keep these two in sync if either changes); `min_stock_level` = separate, higher restock TARGET, falls back to the threshold when unset. `reorderTargetFor()`/`effectiveReorderThreshold()` in admin.html, mirrored server-side in `_lib/stock-alerts.js`.
- **Low-stock email alerts**: `_lib/stock-alerts.js`'s `recomputeStockAndAlert()` is the single choke point every stock-quantity change goes through (manual +/-, invoice auto-deduct, initial-stock insert) — fires an email only on the CROSSING into low stock (not every still-low movement after), tracked via `low_stock_alerted_at`, cleared on restock or on threshold edit. Email shows current qty + how many to order to reach target.
- **Auto-deduct stock on invoice**: `_lib/stock-deduct.js`'s `deductStockForOrder()` matches garment line `breakdown[]` rows (supplier_code+colour+size) against `stock_items`, called from both `orders.js` invoice-creation paths. `restoreStockForOrder()` is the reverse (used on permanent order delete — see Trash below).
- **Stock↔Order linking**: `stock_movements.order_id` links a deduction back to the order that caused it. Stock tab's "Allocated to" ▸ dropdown per item shows only order-linked movements (manual adjustments filtered out per Martin's request), each clickable through to the order (`openOrderFromStock`/`openOrderByNumber` — the latter is a fallback for pre-order_id movements that resolves by parsing the doc number out of the free-text reason).
- **Live stock in the Quote/Invoice builder**: `loadStockLevelsIndex()` builds a flat `code|colour|size → qty` index when the builder opens; each breakdown row shows "N in stock → M left" live as qty is typed (surgical DOM update, not a full re-render, so typing never loses focus).
- **Stock-shortfall flashing bell**: `orderStockShortfall()` in admin.html checks an order's garment lines against the same stock index; a genuinely-blinking (not Tailwind's fade-based `animate-pulse`) red "🔔 Stock shortfall" badge appears on Quotes & Invoices rows AND in the Stock item's own "Allocated to" dropdown (same CSS class `stock-shortfall-flash`, defined in a `<style>` block right after the Tailwind CDN `<script>` tag in `<head>`).
- **Printable Reorder List**: 🖨 button on Stock, opens a `window.open`+`document.write`+`window.print()` page (same pattern as `printOrder()`) listing everything at/below threshold with an Order-qty column against the restock target.
- **Bulk Add Stock**: search→pick colour/size→queues a line→resets for next code, all saved in one POST at the end.
- Dashboard: DECORATION METHODS bar list now also shows revenue (not profit — no cost concept exists for decorations in the schema) alongside the existing count.

### "The Hayley incident" → universal Trash system (the big one)
Martin deleted a real invoice (Hayley's, INV-0022) by testing the app himself. It was **permanently gone** — order deletion was a hard `DELETE FROM orders`, no soft-delete existed for anything except Customers, and the daily backup (only runs once ~24h) had run *before* the invoice was even created, so it wasn't in any snapshot either. Fully unrecoverable; confirmed via D1 query (no `order_events`, no `stock_movements`, no `payments` trace — `deleteOrderPaymentsAndLogs` purges `order_events` too on delete, so even the Activity Timeline was gone).

Martin's response: build a universal Trash bin, "same as a PC's Recycle Bin," across everything deletable in the portal. Built and shipped same session:

- **Soft-delete backend** added to `orders.js`, `stock.js`, `products.js` (Garments/Services), `design-proofs.js` — each gets a `deleted_at` column, `?trash=1` GET, `PUT {restore:true}`, and `DELETE` now soft-deletes by default (`permanent:true` does the real cascade-cleanup delete, e.g. `orders.js`'s permanent delete is the only path that calls `restoreStockForOrder`/deletes payments+events+proofs — a soft-deleted order still conceptually exists, so none of its side-effects get undone until it's actually purged). Customers already had this pattern (`customers.js`) — that's what the rest was modeled on.
- `products.js`: only per-id/per-ids delete goes through Trash — the bulk supplier-wipe and reset-prices import-correction tools deliberately stay hard operations (would otherwise flood Trash with thousands of rows from one bad-import cleanup).
- `design-proofs.js`: soft-delete leaves the R2 file alone (only `permanent:true` removes it from storage) so a restored proof still has its image.
- **One unified "🗑️ Trash" nav tab** (`admin.html`, new `section-trash`) — `loadTrash()` fetches `?trash=1` from all five APIs in parallel, merges into one list via a `TRASH_TYPES` dispatch table (each entry: which API, how to label/title/detail a row, and a `category(row)` function — needed because a single "order" row is either Quote or Invoice depending on `doc_type`, and a single "product" row is either Garment or Service depending on `item_type`). **Filter tabs** (All/Customers/Garments/Services/Quotes/Invoices/Stock/Design Proofs) with live counts filter the already-fetched list client-side, no refetch. **Bulk-select** (checkboxes + top/bottom bulk bar, same pattern as Stock/Customers/Orders) — since a selection can span multiple underlying tables at once, both bulk actions loop one request per row dispatched via `TRASH_TYPES[entry.type].url`.
- Old Customers-only trash modal (`openCustomerTrash` etc.) was fully removed — its button now just does `switchTab('trash')`.
- Every "Delete" confirmation across Orders/Stock/Garments/Services was reworded from "This cannot be undone" to "You can restore it from Trash afterward if needed" (Customers already had this wording — everything now matches).
- **Verified live, full cycle, for every type**: created a throwaway test row → deleted (confirmed disappears from main list, appears in Trash) → restored (confirmed reappears correctly, e.g. stock quantity intact) → permanently deleted → cleaned up (deleted test rows, reset `counters.invoice` back to its pre-test value each time — **always do this after any test invoice**, the sequence number is real and visible to Martin).

## Style/pattern conventions established (follow these, don't reinvent)

- **Soft-delete (Trash) is now the house style for anything deletable**: `deleted_at TEXT` column (lazy `ALTER TABLE` guard), `?trash=1` GET, `PUT {restore:true}`, `DELETE` soft-deletes unless `permanent:true`. Any *new* deletable entity should follow this from day one rather than needing retrofitting later.
- Ledger-over-raw-value: never edit a running total directly — insert a signed delta row, recompute from `SUM`. Used for `payments`, `stock_movements`. `_lib/stock-alerts.js`'s `recomputeStockAndAlert()` is the one choke point for stock quantity — always route through it (or `deductStockForOrder`/`restoreStockForOrder`, which call it), never hand-roll another `UPDATE stock_items SET quantity = ...`.
- `logOrderEvent(db, orderId, type, label)` for the Activity Timeline; `ORDER_EVENT_ICONS` in admin.html needs a new entry for any new event `type`.
- Every D1 schema change is a guarded `try { ALTER TABLE ... } catch {}` inline in the function file that needs it — no separate migration system. When two files both touch the same table (e.g. `stock.js` and `_lib/stock-deduct.js` both touch `stock_movements`), guard the column in *both* files — either could be the first to run on a given deploy.
- Public/customer-facing pages: no login, unguessable per-order or per-customer token, own exemption block in `functions/_middleware.js`.
- When Martin corrects a design/UX choice, match his stated existing pattern exactly rather than defending a "better" alternative.
- **Always test destructive/data-mutating changes against real live data via a throwaway test row, then clean up completely** — delete the test row, and specifically **reset `counters.invoice`/`counters.quote` back to their pre-test value** every time a test invoice/quote is created (Martin sees and cares about the real sequence number). This was done consistently ~8+ times this session with zero leftover test data.
- Autonomous workflow (Martin's explicit standing instruction): build → test live via curl/D1 → commit → push, without stopping to ask permission for routine changes. Exception: this session's price-write-back feature is explicitly paused pending Martin's decision on test-environment shape + a GitHub token — don't build ahead of that without asking.
